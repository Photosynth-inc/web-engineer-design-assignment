# 現状のAPI仕様

課題の題材となるサービスの、現在のAPIです。
三つのエンドポイントがあります。

## 共通の仕様

### 呼び出した利用者の識別

すべてのAPIは、リクエストヘッダ `X-User-Id` で呼び出した利用者を識別します。
実際のサービスでは認証基盤が発行するトークンから利用者を引きますが、この課題では簡略化しています。

- `X-User-Id` がない、または該当する利用者がいない場合は401を返します
- 呼び出した利用者の所属組織が `suspended` の場合は403を返します

### エラーレスポンスの形式

エラー時は次の形式で返します。
この形式は `docs/adr/0000-api-error-response-format.md` で決めたものです。

```json
{
  "error": "この拠点を閲覧する権限がありません",
  "code": "FORBIDDEN"
}
```

`error` は表示用のメッセージ、`code` は機械判別用の識別子です。

| ステータス | code | 意味 |
| --- | --- | --- |
| 401 | UNAUTHENTICATED | 利用者を識別できない |
| 403 | FORBIDDEN | 権限がない |
| 403 | ORGANIZATION_SUSPENDED | 所属組織が停止中 |
| 404 | NOT_FOUND | 対象が存在しない |

## `GET /api/users/:id`

利用者の詳細を返します。

**利用者**：管理画面、外部の連携先

**権限**：呼び出した利用者と同じ組織に所属する利用者のみ閲覧できます。
別組織の利用者を指定した場合は404を返します（存在の有無を隠すため）。

**レスポンス例**

```json
{
  "id": 1,
  "organization_id": 1,
  "name": "山田",
  "email": "yamada@example.com",
  "created_at": "2025-04-01T09:00:00+09:00"
}
```

外部の連携先は `organization_id` を「この利用者が所属する組織」の意味で読み、連携先側のデータと突き合わせています。

## `GET /api/organizations/:id/users`

組織に所属する利用者の一覧を返します。

**利用者**：管理画面

**権限**：呼び出した利用者の所属組織のみ指定できます。
別組織を指定した場合は404を返します。

**レスポンス例**

```json
{
  "users": [
    { "id": 1, "organization_id": 1, "name": "山田", "email": "yamada@example.com" },
    { "id": 2, "organization_id": 1, "name": "佐藤", "email": "sato@example.com" }
  ],
  "total": 2
}
```


## `GET /api/sites/:id`

拠点の詳細を返します。

**利用者**：管理画面

**権限**：呼び出した利用者の所属組織の拠点のみ閲覧できます。
別組織の拠点を指定した場合は403を返します。
拠点IDは管理画面のURLに出るため存在を隠す必要がなく、権限不足であることを伝えます。

**レスポンス例**

```json
{
  "id": 1,
  "organization_id": 1,
  "name": "A社 本社",
  "address": "東京都..."
}
```

**403の例**（`X-User-Id: 3` で `GET /api/sites/1` を呼んだ場合）

```json
{
  "error": "この拠点を閲覧する権限がありません",
  "code": "FORBIDDEN"
}
```
