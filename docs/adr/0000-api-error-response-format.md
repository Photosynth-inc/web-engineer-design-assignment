# [ADR] APIのエラーレスポンスにエラー種別を持たせる

## ステータス

Accepted

## コンテキスト

このAPIは、管理画面と外部の連携先の両方から呼ばれる。
エラー時のレスポンスは `{ "error": "<メッセージ>" }` の一種類で、管理画面はこのメッセージをそのまま画面に表示している。

連携先から「エラーの種類を機械的に判別したい」という要望が来た。
HTTPステータスだけでは、同じ403でも「権限がない」と「組織が停止中」を区別できない。

制約は次の二つ。

- 連携先は、すでに `error` 項目を読んでいる実装が一つある。項目の意味や有無を変える場合は告知が必要
- 管理画面は別チームが保守しており、今回の変更に合わせて手を入れられない

## 決定

案Aを採用する。
`error` はそのまま残し、機械判別用の `code` を横に足す。

案Bは複数のエラーを一度に返せる利点があるが、現時点でその要件はない。
案Aは既存の項目を変えないので、連携先への告知も管理画面の修正も要らない。
複数のエラーを返す必要が出たときに、改めて別のADRで決める。

## 検討した案

### 案A: `error` を残し、`code` を横に足す

```json
{ "error": "この拠点を閲覧する権限がありません", "code": "FORBIDDEN" }
```

**メリット**

- 既存の項目を変えないので、連携先も管理画面もそのまま動く
- 追加する項目が一つで、実装が小さい

**デメリット**

- 一つの応答に複数のエラー（バリデーションの複数項目など）を載せられない
- `error` と `code` のどちらを正とするかが暗黙になる。運用上は `code` を正とし、`error` は表示用と決める

**移行の手順**

1. 全エンドポイントのエラー応答に `code` を追加する

### 案B: `errors` の配列に統一する

```json
{ "errors": [ { "code": "FORBIDDEN", "message": "この拠点を閲覧する権限がありません" } ] }
```

**メリット**

- 複数のエラーを返せる
- `code` と `message` の役割が構造で分かれる

**デメリット**

- 連携先の既存実装（`error` を読む）に影響し、告知と切り替え期間が要る
- 管理画面の修正を別チームに依頼する必要がある

**移行の手順**

1. 全エンドポイントのエラー応答を `errors` 配列にし、当面 `error` も併記する
2. 連携先に告知し、切り替え期間を置く
3. 管理画面の修正を別チームに依頼する
4. 切り替え完了を確認してから `error` の併記をやめる

## 比較表

| 評価軸 | 案A | 案B |
| --- | --- | --- |
| エラー種別の判別 | できる | できる |
| 複数エラーを返せるか | 返せない | 返せる |
| 連携先への影響 | なし | 告知と切り替え期間が要る |
| 管理画面への影響 | なし | 修正が要る |
| 実装の大きさ | 小 | 中 |

## 確認したいこと

- バリデーションで複数項目のエラーを返す要件が、今後の計画にあるか（あるなら案Bを先に取る価値がある）
